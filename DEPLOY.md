# Деплой на BotHost (bothost.ru)

RakSAMP-клиент портирован на headless Linux и управляется через Telegram-бота.
BotHost работает на Linux и поддерживает свой `Dockerfile` — этим и пользуемся.

## Что внутри

- `rakfk/` — C++ исходники RakSAMP 0.3.7 + `CMakeLists.txt` (сборка `raksamp` под Linux).
- `tgbot/` — Python-супервизор (aiogram 3): запускает `raksamp`, шлёт команды в его
  stdin, читает stdout-лог и пересылает в Telegram.
- `Dockerfile` — двухстадийная сборка: компилирует C++ → `/opt/rakb/bin/raksamp`,
  ставит Python-бота в `/opt/rakb`. Код лежит в `/opt/rakb`, а не в `/app`.

## Важные особенности BotHost (учтены в проекте)

1. **`/app` монтируется из Git при запуске** и скрывает всё, что образ положил в
   `/app`. Поэтому бинарник и код бота живут в `/opt/rakb`.
2. **`/app/data` — персистентный том** (тарифы Basic/Pro). Туда пишутся конфиг
   (`instance.json`), `RakSAMPClient.xml` и логи. На бесплатном тарифе данные
   стираются при рестарте.
3. **Порт**: контейнер слушает `0.0.0.0:$PORT` (health-эндпоинт). Telegram работает
   через long polling — публичный URL/вебхук не нужен.
4. **Свой Dockerfile**: команду запуска задаёт `CMD` из Dockerfile, поле «Главный
   файл» игнорируется.

## Шаги

1. **Токен и ID.** Создайте бота у [@BotFather](https://t.me/BotFather), получите
   `BOT_TOKEN`. Узнайте свой числовой Telegram ID (например, у [@userinfobot](https://t.me/userinfobot)).

2. **Репозиторий.** Запушьте этот репозиторий в GitHub/GitLab (или загрузите ZIP в
   панель BotHost). В корне должны быть `Dockerfile`, `requirements.txt`, `rakfk/`, `tgbot/`.

3. **Создайте бота на BotHost.** В дополнительных настройках включите
   **«Использовать собственный Dockerfile»** и укажите `Dockerfile` из корня.

4. **Переменные окружения** (панель → «Переменные окружения»):

   | Переменная | Значение | Обязательно |
   |---|---|---|
   | `BOT_TOKEN` | токен от BotFather | да |
   | `ADMIN_IDS` | ваши числовые ID через запятую, напр. `123456789` | да |
   | `PORT` | `8080` | нет (по умолчанию 8080) |
   | `DATA_DIR` | `/app/data` | нет (по умолчанию /app/data) |
   | `AUTOSTART` | `1` — запускать клиент сразу при старте контейнера | нет |

5. **Персистентное хранилище.** Включите том `/app/data` (Basic/Pro), чтобы конфиг
   и логи переживали перезапуски.

6. **Деплой.** Соберите и запустите. В логах контейнера будет
   `health on 0.0.0.0:8080 | admins=... | bin=/opt/rakb/bin/raksamp`.

## Управление из Telegram

Откройте бота (команды доступны только `ADMIN_IDS`):

```
/run                          # запустить клиент
/connect 1.2.3.4 7777 MyNick  # сервер + ник (опционально пароль 4-м аргументом)
/auth password                # авторизация на сервере (!auth)
/spawn                        # заспавниться
/mode 3                       # runmode: 1 bare, 2 still, 3 normal, 4 follow, 5 follow+veh
/say привет                   # сообщение в чат
/scmd login 123               # серверная команда (/login 123)
/players                      # список игроков (с выводом)
/teleport                     # список телепортов; /teleport <id> — перейти
/dialog 5 1 0 text            # ответ на диалог сервера
/cmd !pos x 100               # любая команда RunCommand
/log on                       # живой лог в этот чат (батчами ~1.5с)
/logs 50                      # последние 50 строк лога
/status                       # состояние процесса/подключения
/config                       # текущий конфиг
/query [ip] [port]            # UDP-проверка доступности сервера (диагностика)
/nettest [ip] [port]          # референс-серверы + цель: блок хоста vs блок цели
/stop · /restart
```

Серверные диалоги в headless-режиме приходят в лог как `[DIALOG] id=... title=...`
— отвечайте `/dialog <id> <button 0/1> <item> <text>`.

## Сеть

SA-MP/RakNet ходит по **UDP**. Исходящий UDP из контейнера должен быть разрешён
(стандартный Docker bridge это позволяет). Если тариф/фаервол режет UDP — клиент
не подключится; уточните у поддержки BotHost.

### Если `/connect` даёт «Connection attempt failed» на живом сервере

Сначала `/nettest <ip> <port>` — он шлёт UDP-запросы на 3 публичных референс-сервера
и на вашу цель, и сразу говорит, где проблема:

- **референсы 🟢, цель 🔴** → исходящий UDP на хосте работает, молчит именно цель
  (неверный ip/port, сервер оффлайн, или он фаерволит IP контейнера). Пробуйте
  «Зарубежный IP» + новый деплой, либо проверьте адрес.
- **все 🔴** → исходящий UDP закрыт на хосте. SA-MP не заработает; нужен VPS с
  открытым UDP или запрос в поддержку BotHost.

**Поддомен/вебхук не помогает.** Домен, который выдаёт BotHost (`xxx.bothost.ru`), —
это *входящий* HTTPS для вебхука Telegram. Он не открывает *исходящий* UDP к игровому
серверу и не меняет протокол. Подключение к SA-MP по имени сервера вместо IP тоже не
поможет: DNS лишь резолвится в тот же IP, транспорт остаётся UDP.

Одиночный `/query <ip> <port>` — то же самое, но только по одной цели:

- **🟢 UDP OK** (пришли hostname/players) → исходящий UDP работает, сервер доступен.
  Значит проблема на уровне игрового протокола (версия/cookie или сервер режет
  именно игровое подключение), а не сети.
- **🔴 no UDP response** → исходящий UDP режется хостом, либо сервер фаерволит IP
  контейнера. Что попробовать:
  1. В профиле BotHost включите **«Зарубежный IP»** (или наоборот выключите) и
     сделайте **новый деплой** — сменится исходящий IP, сервер может пускать другой.
  2. Уточните у поддержки BotHost, разрешён ли **исходящий UDP** на вашем тарифе.
  3. Если UDP на хостинге принципиально закрыт — SA-MP там не заработает; нужен
     VPS/хостинг с открытым исходящим UDP.

## Локальная проверка

```bash
# сборка клиента
cmake -S rakfk -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build -j

# бот локально (бинарник рядом)
pip install -r requirements.txt
BOT_TOKEN=... ADMIN_IDS=123456789 \
  RAKSAMP_BIN=$PWD/build/bin/raksamp DATA_DIR=$PWD/data PORT=8080 \
  python -m tgbot
```

Через Docker:

```bash
docker build -t rakb-tg .
docker run --rm -p 8080:8080 \
  -e BOT_TOKEN=... -e ADMIN_IDS=123456789 \
  -v rakb-data:/app/data rakb-tg
```

## Туннель UDP-over-TCP (оставить бота на BotHost)

Если `/nettest` показал «все 🔴» (хост режет исходящий UDP), бота можно **оставить на
BotHost**: его UDP-трафик пойдёт поверх TCP до небольшого реле на VPS с открытым UDP.
Исходящий TCP на BotHost работает (так ходит Telegram polling).

```
raksamp ─UDP─► 127.0.0.1:7777 (прокси в контейнере) ─TCP─► реле (VPS) ─UDP─► SA-MP
```

Шаги:

1. Поднимите реле на VPS с открытым UDP — см. `relay/README.md` (чистый Python без
   зависимостей, есть systemd-юнит и Docker). Запомните токен и откройте входящий TCP 9000.
2. В панели BotHost добавьте переменные:
   - `TUNNEL_RELAY=VPS_IP:9000`
   - `TUNNEL_TOKEN=<тот же токен, что RELAY_TOKEN>`
3. **Новый деплой.** Теперь `/connect <ip> <port> [nick]` автоматически идёт через
   туннель (клиент dial-ит локальный прокси, реальный адрес несёт туннель до реле).
4. Проверка: `/tunnel` — покажет `relay connected: true`, target, счётчики байт.
   Затем `/connect ...` должен дать 🟢.

Команда `/tunnel` показывает статус туннеля. Если `TUNNEL_RELAY` не задан — туннель
выключен и `/connect` работает напрямую (как раньше).

## Запасной вариант: VPS (если хостинг режет исходящий UDP)

Бесплатный путь — **Oracle Cloud Always Free**: пошагово в [`ORACLE-FREE.md`](ORACLE-FREE.md),
деплой одной командой через [`scripts/deploy-vps.sh`](scripts/deploy-vps.sh).

Образ самодостаточный: C++-runtime слинкован статически, нужен только glibc, всё
управление идёт через Telegram long polling (входящий порт не требуется). Поэтому
тот же образ запускается на любом VPS с Docker и открытым исходящим UDP — без
привязки к BotHost и его `/app`-монтированию.

```bash
# на VPS (Debian/Ubuntu), Docker уже установлен
git clone https://github.com/WeteroScript/Rakb.git
cd Rakb
git checkout arena/3b12d5df-rakb

docker build -t rakb .
docker run -d --name rakb --restart unless-stopped \
  -e BOT_TOKEN="123456:ABC..." \
  -e ADMIN_IDS="123456789" \
  -e AUTOSTART="1" \
  -v rakb-data:/app/data \
  rakb
```

Проверка:

```bash
docker logs rakb        # строка health on 0.0.0.0:8080 | admins=... | bin=...
```

Затем в Telegram: `/nettest <ip> <port>` — на VPS с открытым UDP референсы и цель
должны ответить 🟢, после чего `/connect <ip> <port> <nick>` подключается.

Публичный порт открывать не нужно (health-эндпоинт слушает внутри контейнера;
Telegram работает через исходящий polling). Если хочется health снаружи — добавьте
`-p 8080:8080`. Большинство VPS-провайдеров (Hetzner, OVH, Vultr, DigitalOcean и т.п.)
исходящий UDP не режут; для RU-серверов берите ноду ближе к ним ради пинга.
